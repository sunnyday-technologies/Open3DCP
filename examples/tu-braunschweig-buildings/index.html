Example entry · the project / process layer

TU-Braunschweig 3DCP Buildings → Open3DCP

A catalogue of as-built printed buildings — not mixes, not strengths. It lights up a different slice of the digital twin: the project/process layer the connective schema has to reach next. The missing materials data is the whole point.

storable · CC BY 4.0 3D-printed buildings · Source: Zenodo · DOI 10.5281/zenodo.14214812 · provenance · attribution

1 · Native structure

Storage medium: a single flat table (.xlsx), one row per built project, 22 project/process categories. ~175 projects (2013–2023) in the source; a 10-record, landmark excerpt is committed here.

Source field (data class)Role in the digital twin
Year · Country · Citywhen / where (provenance)
Project Consortium · Building Companywho (provenance)
Printer · Printer Typeprocess — the printing system
Fabrication / Printing Strategyprocess — off-site vs in-situ, segmentation
Storeys · Square Meter · Purpose · Type of Buildingthe as-built artefact
(no mix, rheology, or strength fields)— absent by design —
Why this matters even with no materials data. Open3DCP's flat schema is mix-centric, so almost none of these project fields has a typed home today — they are curated as named project-layer columns + provenance, with no fidelity score. That gap is the signal: a full digital twin must link the as-built project (this layer) to the mixes (UCI / Meta) and the prints (UF / RILEM). No single source spans all three; the union does.

3 · Result in Open3DCP

project layer · no mix score is_3d_printed is set; everything else is a project/process-layer field recorded as named columns + provenance. No fidelity score — this is a layer beyond the current flat mix schema, not a lossy mix conversion. A future Open3DCP project/process table would type these fields and link them to the mixes and prints used.
